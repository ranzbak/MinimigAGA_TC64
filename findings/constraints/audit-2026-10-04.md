## 1. Assessment per constraint file

### clocks.xdc  (correct, one documentation nit)

  (clk_114, clk_sd_114 at -121.5 deg, dll_28, clk_38), one on the HDMI MMCM (clk_148). The

### sdram.xdc  (constraints are RIGHT; the design is marginal -- see section 2.A)
- Pins, IOSTANDARD LVTTL DRIVE 12 SLEW FAST on all `dr_*`.
- `:62` `create_generated_clock clk_gen_sdram` on the port, sourced from CLKOUT1: correct
  model of the forwarded clock including BUFG_SDR -> fabric route 2.52 ns -> OBUF 2.98 ns
  (slow). Note that route: `dr_clk` is driven straight from the BUFG net through the fabric
  to an OBUF (`facts.txt`: driver `BUFG_SDR/O`), 9.68 ns clock-out at slow / 3.62 ns at
  fast -- a 6 ns PVT spread on the forwarded clock, which is what makes the read side
  corner-dependent.
- `:70-74` device numbers tSU 1.5 / tH 0.8 / tAC3 5.4 / tOH 2.5 / trace 0.17: match the
  Alliance datasheet for the -7 grade (tAC3 5.4 ns -7, 5.0 ns -6; tOH 2.5 min; also
  `lib/models/AS4C16M16SA.v:75-78`). **The fitted speed grade is not recorded anywhere in
  the repo** (grep for `AS4C16M16SA-` finds nothing) -- needs Paul (section 3).
- `:81-82, :86-87` output/input delay formulas: correct (`-max tSU+trace`, `-min -tH+trace`,
  `-max tAC+trace`, `-min tOH+trace`), fix-01 applied.
- `:94` `set_multicycle_path -setup -end 2` on the read data: expresses "capture on the
  second clk_114 edge after the SDRAM launch edge" (requirement 11.791 ns in the report),
  which is the edge the RTL consumers were validated against (fast corner, boots). Correct.
- `:95` `set_multicycle_path -hold -end 1`: **wrong**. The SDRAM launches a new word on
  every clock during a burst, so the hold check must stay one capture edge before the setup
  edge (Vivado's default once setup is 2). `-hold -end 1` moves it to the edge *before the
  launch*: the report shows requirement -5.840 ns and slack +10.204 ns
  (`sdram_in.rpt`/release report), i.e. no hold check at all on the read data. fix-12
  already found this ("the hold companion was wrong and hid it") but its revert put the
  line back. With the line removed (`exp_sdram_in_hold.rpt`) the check lands on the right
  edge (requirement 2.975 ns = clk_114 rise@8.815 - clk_gen_sdram rise@5.840) and the real
  hold margin is **+1.388 ns** (dr_d[9], fast corner) -- comfortable, so deleting the line
  changes nothing on hardware and makes the report truthful. Also `exceptions_ignored.rpt` lists both port-scoped rules as
  "Non-existent path" while report_timing applies them -- the known port-scoped quirk.

### adv7511_video.xdc  (interface untimed by design; IOB packing verified; data for the

  FAST (`hdmi_cells.txt`). On a DDR bus whose sync lines are sampled on the same edge as

- `:46-49` false paths on dv_int, I2C, cecclk: fine (resynchronised in RTL / no requirement).

  **no setup/hold check exists on the ADV7511 bus** (check_timing: 16 outputs "no output
  delay but user has a false path").
- `:68` IOB=TRUE: **verified effective** in the routed design -- all 15 output registers
  (clk_pixel_out, de_out, hsync_out, vsync_out, data_out[11:0]) are in OLOGICE2.OUTFF
  (`hdmi_cells.txt`). `report_datasheet` (datasheet.rpt:134-149) gives clock-to-pin

  dv_de/hsync/vsync in the same band: pin-to-pin skew about 0.07 ns worst in each corner.
  So with the current RTL (data on the opposite clk_148 edge from the forwarded clock,
  `adv_ddr.v:64-95`) the data transitions sit nominally 3.37 ns either side of each
  dv_clk edge at the pins, minus ~0.07 ns skew, minus the ADV7511's tVSU/tVHLD.
  **The output timing is sound as built; what is missing is a constraint that would
  catch it changing** (a build where a register is not packed, or a future RTL change).

## 2. Findings in detail, with severity

Severity key: HW = could cause real hardware failure; LUCK = timing-luck instability
between builds; HYG = hygiene / reporting.

### A. SDRAM read capture: real violation, not a constraint error  (HW)
Evidence: release timing_summary.rpt:2039-2100. Path `dr_d[11] -> sdram/sdata_reg_reg[11]/D`,
slow corner: launch clk_gen_sdram rise@5.840; clock-out to pin 9.679 ns; input delay
5.570 (tAC3 5.4 + 0.17); IBUF 1.499 + route 0.721; arrival 23.308 vs required 22.860
(capture clk_114 rise@17.631 + insertion 5.313 - uncertainty 0.217 incl. 0.120 MMCM phase
error) -> **-0.448 ns**. Every build since September shows -0.45 +/- 0.1 on these 16
endpoints (stage_r01ldx: -0.47); the spread is route-only (0.72 ns IBUF->FF route).

Is the constraint right?
- Clock relationship: right (clock at the pin, phase -121.5 deg, all delays included).
- Input delay: right for a -7 part. For a -6 part (tAC3 5.0) the slack would be -0.05.
- Multicycle -end 2: right -- it names the edge the RTL consumers use (sdram-read-path.md,
  sdram-sim-results.md: fast corner word 0 on ph8 = 2nd edge; slow corner lands on the
  3rd = one word late, which is exactly what -0.45 ns says).
- Missing: a correct hold check (sdram.xdc:95 disables it; see exp_sdram_in_hold.rpt).
So: the design is one edge marginal at the slow corner, the constraint reports it
honestly, and the "boots after a few resets / warm-board" history is this path.

What the constraints *can* do about it (no RTL):
1. **Re-centre CLKOUT1_PHASE.** Write side has +1.163 setup / +0.987 hold (clk_114 ->
   clk_gen_sdram, `sdram_out.rpt`), read side -0.448 / (hold large). Moving dr_clk
   earlier by d ns moves read setup +d and write setup -d. The in-memory sweep
   (`exp_phase_sweep.txt`, same routed netlist, only the MMCM attribute changed) gives
   the trade-off curve; see the table in section 2.A.1 below. The MMCM phase step for a
   /10 output is 4.5 deg = 0.110 ns. This changes `amiga_clk_xilinx.v:49` (an RTL
   parameter) and nothing in the XDC (clocks.xdc derives the waveform from the MMCM).
   Risk: moderate -- the history (-146.25 -> -144 -> -121.5) shows the phase was tuned
   on hardware before; any change must be checked at BOTH corners in the report AND on
   the board warm. Verify: `clk_gen_sdram -> clk_114` and `clk_114 -> clk_gen_sdram` both
   positive for setup and hold in `report_timing_summary`.
2. **Forward dr_clk through an ODDR** (RTL, 6 lines): removes the 2.5 ns fabric route and
   most of its 6 ns PVT spread from the forwarded clock; `clk_gen_sdram` then sources from
   the ODDR C pin. This shrinks the slow-corner clock-out (read gets earlier data) and the
   corner spread (both directions become predictable). Risk: changes the phase relationship
   at the pin; re-derive CLKOUT1_PHASE from the report afterwards. This is the standard fix
   and is independent of fix-12's failed capture-clock experiment (it touches only the
   clock pin, not the DQ capture).
3. Not recommended: changing -end 2 to -end 3 "to make it pass". That would describe the
   slow-corner behaviour and contradict the RTL table, and the fast corner would then be a
   hold failure (data for word n+1 arrives 1.5 ns after the edge at fast, per
   sdram-sim-results.md). The bench `sim/sdram_timing` is the arbiter for which edge.

Reading: a 0.110 ns step per 4.5 deg, exactly the expected 1:1 trade. -153 deg balances

decides whether -153 is centre (-7) or already read-biased (-6: read +0.72, write +0.39).

### B. ADV7511 (HDMI) outputs: untimed, but measured sound; add a guard constraint  (LUCK)
Facts: all 15 outputs in OLOGIC (hdmi_cells.txt); clock-to-pin skew between dv_clk and
dv_d/de/hsync/vsync <= ~0.07 ns per corner (datasheet.rpt:134-149). With the false path
lifted in memory (`exp_hdmi_paths.rpt`) the per-pin path is OLOGIC FF 0.418 + OBUF ~2.96
ns = 3.377 (dv_d[3], launched on the clk_148 *falling* edge, IS_INVERTED), 3.382 (dv_clk)
and 3.393 (dv_de) at the slow corner -- matched to 0.02 ns, no fabric route at all. The
paths report `Slack: inf` because there is no output delay to check against; data launched on the opposite
clk_148 edge from the pixel clock (adv_ddr.v:80-95), so nominal setup = hold = 3.37 ns
at the ADV7511 pins before its own tVSU/tVHLD and the programmed clock delay
(0xBA = 0x20, -0.8 ns, fw/ctrl_832/adv7511.c:46; the RTL table has the same).
ADV7511 datasheet (web search summary, to be confirmed on the PDF): tVSU 1.0 ns,
tVHLD 0.7 ns (the ADV7511W variant: 1.8 / 1.3). That leaves ~2 ns each side -- the
monitor-loses-sync issues are therefore unlikely to be pin timing of this bus *as built*.
What IS a risk: the whole interface depends on `IOB=TRUE` succeeding on every build and
on nobody adding logic between the `*_v2` registers and the pads. A pad flop that fails to
pack (e.g. after a reset or enable gets added) silently moves by several ns and nothing
in the timing report changes, because the group is false-pathed.

Constraint options:
1. (Now, XDC only) Keep the false path but make the build **fail loudly** on skew: add to
   build_ap040.tcl a post-route check that every `my_pal_to_ddr/myadr_ddr/*_out_reg*` has
   `BEL =~ OLOGICE2*` and that `report_datasheet` clock-to-pin for dv_* differs from
   dv_clk by < 0.3 ns at both corners; `error` otherwise. Zero timing risk.
2. (Now, XDC only, approximate) Replace the false path by a **virtual clock** check that
   bounds the data pins relative to the clock pin: a virtual clock `dv_vclk` with the
   clk_148 waveform shifted by the dv_clk clock-to-pin delay cannot be expressed exactly
   (the delay is corner-dependent), so this is a `set_max_delay`/`set_min_delay` pair from
   `[get_clocks clk_148]` to the dv data ports bounding clock-to-pin to e.g. [3.0, 10.0] ns
   plus the same on dv_clk. It catches a lost IOB pack (fabric route adds 1-8 ns) but is
   not a tsu/th check. Low risk; two TIMING-47 style warnings.
3. (Right fix, RTL + XDC, fix-03) Forward dv_clk with an **ODDR** on clk_148 (D1=1,D2=0
   gated by the pixel phase, or run the ODDR from a 74.25 MHz BUFG and move data_out to
   that clock), then
   ```
   create_generated_clock -name dv_clk_out -source [get_pins .../dv_clk_oddr/C] -divide_by 2 [get_ports dv_clk]
   set dv_data [get_ports {dv_d[*] dv_de dv_hsync dv_vsync}]
   set_output_delay -clock dv_clk_out -max [expr {1.0 + $tr}]  $dv_data
   set_output_delay -clock dv_clk_out -min [expr {-0.7 + $tr}] $dv_data
   set_output_delay -clock dv_clk_out -max [expr {1.0 + $tr}]  -clock_fall -add_delay $dv_data
   set_output_delay -clock dv_clk_out -min [expr {-0.7 + $tr}] -clock_fall -add_delay $dv_data
   ```
   with the ADV7511 values confirmed from the datasheet and the 0xBA delay accounted for
   (the ADV samples 0.8 ns early: effectively tsu 1.8 / th -0.1 at the pin in the current
   setting). Then the firmware clock-delay knob becomes a documented centring step rather
   than a tuning. Risk: RTL change on a working interface; the half-cycle data shift of
   2026-09-24 must be preserved. Verify: report_timing to dv ports shows real requirements
   on both edges; check_timing MEDIUM count drops by 16.
Also: set SLEW FAST on dv_hsync/dv_vsync (adv7511_video.xdc:19-20) -- the only two bus
members that differ. (Note the reported skew already includes the slower slew in the OBUF
model; keep it consistent anyway.)

### C. Reset into clk_148 is still unsynchronised (fix-11 open)  (LUCK, functional)
`myReset/nresetLoc_reg` (dll_28) drives R/CE of ~100 clk_148 registers directly
(cdc_details.rpt: CDC-1/CDC-11 rows `nresetLoc_reg/C -> my_pal_to_ddr/.../R|CE`,
e.g. hd_50hz_gen/r_r_reg, myadr_ddr/data_int_reg; worst path +0.557 ns against the
6.734 ns datapath bound, `tp_dll_28__clk_148.rpt`). The bound keeps it short but each
register leaves reset on its own clk_148 edge. The frame generator re-syncs to vsync so
the steady state is fine; a reset while running (user reset) can leave the 50/60 Hz
generator counters one cycle apart for a frame. Fix is RTL (a 2-FF ASYNC_REG synchroniser
for `reset` inside pal_to_ddr on clk_148), then the CDC rows become CDC-9/Info. Not a
constraint change.

### D. HDMI offset bus crosses without a handshake  (HYG; functionally quasi-static)
`mycfide/vpos_interface.pos_data_q[15:0]` (clk_114) -> `my50hzupsample/r_addrb` (clk_148)
through subtraction logic (cdc_details.rpt:396-405, CDC-15, 10+ endpoints, bounded by the
6.734 ns rule). Changes only when the user moves the picture in the OSD; a torn value
lasts one line. Add a reviewed `create_waiver -type CDC -id CDC-15` with that reason, as
ddr3.xdc does, so the row does not hide the next real one (item H).

### E. clk_114 -> clk_148 synchronisers  (HYG)
`s_pal_vsync_reg[1]` fans out to three synchronisers (CDC-11 x3: my50hzupsample,
my60hzupsample, myfreq) and `s_next_buf` lacks ASYNC_REG (CDC-2 x2, TIMING-10). Fan-out
from one launch flop to several 2-FF chains is a real (small) hazard: the three copies can
disagree for a cycle. RTL: one synchroniser, fan out after it; add `(* ASYNC_REG *)` on
s_next_buf. The `TIMING-9 Unknown CDC` is the unsynchronised reset of item C.

### F. DDR3 pins unconstrained  (HYG for the calibrated DQ/DQS; LOW-MEDIUM for cmd/addr)
See ddr3.xdc assessment. Proposed XDC (needs Micron tIS/tIH and the board's CK/ADDR
trace delta, else use conservative 1.0 ns):
```
# DQ/DQS: captured by IDELAYE2+ISERDESE2 with a runtime tap sweep; static delays are not meaningful
set_false_path -from [get_ports {ddr3_dq[*] ddr3_dqs_p[*] ddr3_dqs_n[*]}]
set_false_path -to   [get_ports {ddr3_dq[*] ddr3_dqs_p[*] ddr3_dqs_n[*] ddr3_dm[*]}]
# CK is ~clk_ddr100 straight to the pad; command/address are IOB flops on clk_ddr100
create_generated_clock -name clk_ddr3_ck -source [get_pins ddr3_island/u_pll/u_plle2/CLKOUT0] -divide_by 1 -invert [get_ports ddr3_ck_p]
set ddr3_cmd [get_ports {ddr3_addr[*] ddr3_ba[*] ddr3_ras_n ddr3_cas_n ddr3_we_n ddr3_cke ddr3_odt ddr3_reset_n}]
set_output_delay -clock clk_ddr3_ck -max [expr {$tIS + $tr}] $ddr3_cmd
set_output_delay -clock clk_ddr3_ck -min [expr {-$tIH + $tr}] $ddr3_cmd
```
Caveat: the inverter is a LUT1 (`u_pll/u_pad_ck_i_1`); Vivado will propagate the
generated clock through it (a LUT is a combinational cell, unlike the FDRE case of
dv_clk) but may warn. Verify: check_timing HIGH 56 -> 0; `clk_ddr100 -> clk_ddr3_ck`
appears in the inter-clock table with positive slack. If it does not meet, the LUT route
is the reason and an ODDR for CK is the RTL fix. Also DDR3 DLL-off at CK = 100 MHz is
outside JEDEC's DLL-off range (125 MHz min, per the vendored README's own caveat line
191-194) -- not a constraint matter, noted because of the open DDR3 crash.

### G. Hold margins on the synchronous MMCM-sibling crossings are 14-130 ps  (LUCK)
dll_28 -> dll_28 hold +0.014 (`autoconfig/board_base_addr -> GARY1/toccata_base_addr`),
clk_114 -> dll_28 +0.036, clk_38 -> clk_38 +0.064, clk_114 -> clk_114 +0.069,
dll_28 -> clk_114 +0.106, clk_114 -> clk_38 +0.112 (tp_*.rpt, release report WHS 0.014).
These are fast-corner hold checks on direct FF->FF paths; the router fixes hold as a hard
requirement, so they are not expected to go negative, but 14 ps says the router had to
work for it. They are correct constraints; nothing to change. If a build ever reports
WHS < 0 on one of these pairs, the fix is `set_clock_uncertainty -hold` is NOT it -- it is
to check BUFG placement (BUFGCTRL_X0Y1 vs X0Y8) and MMCM->BUFG routes.
