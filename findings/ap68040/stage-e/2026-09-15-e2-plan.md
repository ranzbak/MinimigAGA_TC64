# Stage E2 — One 32-bit Memory Port: Implementation Plan (DRAFT, decisions pending)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The AP68040 reaches SDRAM and DDR3 over one 32-bit request/acknowledge port instead of the 32→16→32 adapter chain, with the D3 placement rule in one visible block, and SysInfo still ≥ 0.28x.

**Architecture:** Every bus master (the core's `m_*` channel and the MMU walker) sits on clk_38 behind one mux. One router decodes each request once. RAM requests go to a clk_114 sequencer that drives a new "unit" port on `cpu_cache_new`, shared by `sdram_ctrl` and `ddr3_fastram`. Everything else (custom chips, CIAs, Akiko, undecoded space, the NMI vector) keeps today's 16-bit path through `ap040_bus16_adapter`, bit for bit. Completion goes back to the core as ONE clkena-shaped pulse, with the read data captured on that same edge.

**Tech Stack:** VHDL-93 (wrapper), Verilog (controllers, AP68040 overlay), xsim (`sim/ddr3_cpu`), iverilog (`sim/sdram_coherency`, `sim/ddr3`), Vivado 2023.2.

**Spec:** [2026-09-15-stage-e-design.md](2026-09-15-stage-e-design.md) §4 approach 1 and §5 E2 (O1–O5 taken as recommended, Paul 2026-09-15). Inputs from this week: [e0-e1-results.md](e0-e1-results.md) (placement monitor; the step-2 read/write split), [e4a-results.md](e4a-results.md) (dead code removed, suite numbers).

### What the code says (why the spec needs amending)

1. **`b_*` does not exist outside the core.** It is internal to `lib/AP68040/rtl/ap040_tg68k_compat.v` (wires at :192–197, adapter instance :483–508). The wrapper only sees the 16-bit bus. Taking `b_*` natively needs a change in the AP68040 tree.
2. **Both controllers share one CPU front end.** `sdram_ctrl.v:296` and `ddr3_fastram.v:252` both instantiate `cpu_cache_new`, whose CPU side is the 16-bit port. Its memory side is already 32-bit writes (`sdr_dat_w[31:0]`, 4 byte selects) and whole-line reads. A 32-bit CPU side on `cpu_cache_new` serves both controllers at once, so E3's front end comes along with E2.
3. **The walker and fill routers cannot stay unchanged.** Both borrow the 16-bit RAM port (`TG68K.vhd:579–595`), and that port goes away. They are also the reason `bus_step`, `bus_fresh` and a `cpu.xdc` multicycle exception exist (`TG68K.vhd:1510–1577`, `:1383–1392`).
4. **The AP68040 has never had registered read data.** ba323b9 ("capture datatg68 with the enable") was wired into the TG68K kernel's `data_in`, not the AP68040's. At `d3_stable` the AP040 instance maps `data_in => datatg68` (in `g_ap040`), and since E4a removed `g_tg68k`, `datatg68_r` (`TG68K.vhd:306`, `:1400`) is assigned and never read. The hardware test on 2026-09-13 ("still corrupts") therefore never tested the fix on this core. The read-data crossing is still in neither D4 category: not stable across the capture window, not an edge-shaped pulse. It is a live suspect for the unexplained 3/7/11/15 mechanism.

## The unit port (D3)

On `cpu_cache_new`, passed straight through by `sdram_ctrl` and `ddr3_fastram`, all clk_114:

| Signal | Dir | Meaning |
|---|---|---|
| `cpu_req` | in | Level. All fields below stable while high (category 1 from `ram_seq`) |
| `cpu_we` | in | Write |
| `cpu_ir` | in | Instruction fetch (selects the I ways); a data read otherwise |
| `cpu_wadr[25:1]` | in | Word address of word A |
| `cpu_bs[3:0]` | in | Active-high byte selects `{A hi, A lo, A+2 hi, A+2 lo}`. `cpu_bs[1:0] != 0` means a two-word unit |
| `cpu_wdat[31:0]` | in | `{word A, word A+2}` |
| `cpu_rdat[31:0]` | out | `{word A, word A+2}`, valid with `cpu_ack` |
| `cpu_ack` | out | Level. **Only ever high while `cpu_req` is high**; low the cycle after `cpu_req` drops |

Unit invariants (the wrapper guarantees them; `cpu_cache_new` asserts them under `` `ifdef SOC_SIM ``): `cpu_bs != 0`; a two-word unit never crosses a line, i.e. `cpu_bs[1:0] != 0` implies `cpu_wadr[3:1] != 3'b111`.

The acknowledge rule removes the line buffer's "answer before the select" fast path (`cpu_cache_new.v:257–260`), the root of the D3-FIX walker bug and of `bus_fresh`.

**Split table** (`ram_seq`, from `x_size` and `o = x_addr[3:0]`; A is the unit's word address):

| Request | Condition | Units, in order |
|---|---|---|
| B at o | — | 1: A = o with bit 0 cleared; `bs` = `1000` if o even, `0100` if odd |
| W at o | o even | 1: A = o, `bs 1100` |
| W at o | o odd, o ≠ 15 | 1: A = o − 1, `bs 0110` |
| W at o | o = 15 | 2: B at o, B at o + 1 |
| L at o | o even, o ≠ 14 | 1: A = o, `bs 1111` |
| L at o | o = 14 | 2: W at o, W at o + 2 |
| L at o | o odd | 3: B at o, W at o + 1, B at o + 3 |

Read bytes are shifted in big-endian as each unit completes (the adapter's `rshift` rule, `ap040_bus16_adapter.v:171–191`), so `x_rdata` is right-aligned by size exactly as `b_rdata` is today.

What the CPU-side state machine must do (write it test-first, against the sweep):

| State | Entered when | Does | Leaves to |
|---|---|---|---|
| `IDLE` | reset done, `cpu_req` low | registers `cpu_wadr` (the old `cpuAddr_r` "one cycle before" rule becomes "one cycle after `cpu_req` rises": the port never answers in the first cycle) | `REQ` when `cpu_req` |
| `REQ` | request present one cycle | write: update the line-buffer words selected by `cpu_bs` if the line matches, else mark it dirty; queue `{word A, word A+2}` with `~cpu_bs` as `sdr_dqm_w` into the write buffer. Read: line-buffer match → `ACK` with `cpu_rdat` from the buffer | write → `WWAY`; read hit → `ACK`; read miss → `RWAY` |
| `WWAY` | write | update matching ways: one RAM write if `cpu_wadr[1]` = 0 (both words in one 32-bit way entry), two if 1 | `ACK` (posted, today's behaviour; D8 changes this in Task 5) |
| `RWAY` | read miss on the buffer | today's `CPU_SM_READ` way copy, 4 cycles; acknowledge only when the words the unit needs are in the buffer | `ACK`, or `FILL` on a way miss |
| `FILL` | way miss | today's `CPU_SM_FILL1/FILL2`; acknowledge after word A, and after word A+2 too for a two-word unit (the burst starts at A and wraps, so A+2 is the second word delivered); keep filling to 8 words | `ACK`, then back to finishing the fill if `cpu_req` is still high |
| `ACK` | data ready | `cpu_ack` high | `IDLE` when `cpu_req` drops |

### Task 4: Mux, router, `ram_seq` and the clk_38 walker in the wrapper (D4, D6, D7)

**Files:** `rtl/soc/TG68K.vhd`, `rtl/soc/minimig_virtual_top.v`, `fpga/openaars/aars_v5.0/xc7a100t/cpu.xdc`, `sim/ddr3_cpu/run.sh`, `ddr3_cpu_tb.sv`, `real_sdram.vh`, `placement_monitor.vh`.

The blocks, in order of data flow:

1. **Mux (clk_38, combinational).** `x_* = walker when wk_req = '1' else m_*`. The invariant that the core's side is idle while `walker_req` is high (`TG68K.vhd:1244–1263`) is already asserted in `sim/ddr3_cpu`; the assertion stays.
2. **Walker (clk_38 process, `IF clkena = '1'`).** One longword request per descriptor at `wk_addr`, `x_size = L`; answers `wk_ack`/`wk_data` from `x_ack`/`x_rdata`; `wk_berr` on a misaligned address or `sel_undecoded`, as today. Replaces `WK_IDLE/HI/GAP/LO/DONE`.
3. **Router (clk_38, combinational from `x_addr`).** The existing `sel_*` decode, fed `x_addr` instead of `cpuaddr`. `x_ram = (sel_ram OR sel_ddr) AND NOT sel_nmi_vector`. The 16-bit adapter gets `mem_req => x_req AND NOT x_ram`; `ram_seq` gets `x_req AND x_ram`.
4. **`ram_seq` (clk_114).** States `RS_IDLE → RS_SETUP → RS_UNIT → RS_GAP → … → RS_DONE`. It latches the request in `RS_IDLE` (category 1: the core holds `x_*` until it takes the acknowledge on a clkena edge); computes up to three units from the split table; for each unit, puts the fields out in `RS_SETUP`, raises `ram_req`/`ddr_req` in `RS_UNIT` **only when `cpu_phase_ok` is open** (the D3 rule in one place: the gate process moves here unchanged and loses its `slower(0)` term, since `RS_SETUP` now supplies the setup cycle), shifts read bytes in on the acknowledge, and drops the request for one cycle in `RS_GAP`. In `RS_DONE` it holds `ram_done` until the clkena edge that delivers it.
5. **Completion (clk_114, category 2).** In the existing clkena process: `clkena_r <= cpu_ph AND bus_release` with `bus_release = (NOT x_req) OR ram_done OR bus_ready16`, where `bus_ready16` is today's chipset/Akiko/undecoded completion for the adapter branch. On the same edge, `IF (cpu_ph AND ram_done) = '1' THEN x_rdata_r <= ram_rdata_asm; ram_ack_r <= '1'; ELSE ram_ack_r <= '0'`. The core's `m_ack` is `ram_ack_r OR adapter_ack` and `m_rdata` is `x_rdata_r` or the adapter's `mem_rdata`. **This is the registered read data the AP68040 never had (finding 4).**
6. **Deleted:** the fill router (D5 is decided in Task 5; until then `AP040_FILL_CHANNEL => 1` and the fill router is fed from `ram_seq` as a second master, with `fl_ok` as today), `bus_step`, `bus_fresh`, `wk_active_d`, `mem_ready`, `ramcs`, `ddrcs`, `cpustate`, `slower(0)` in the select, and the RAM terms of `datatg68`. `cpu.xdc`: the `bus_step` exception goes; a rule `set_multicycle_path -setup -end 2` from the `ram_seq` latch registers into the kernel keeps the category-1 argument explicit.
