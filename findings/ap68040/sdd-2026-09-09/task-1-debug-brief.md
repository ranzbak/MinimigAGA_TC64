# Task 1 fix round: the x3 core boots to a black screen on hardware while every bench passes

## The symptom
Bitstream build/stage_ap040_x3 (commit 4b033dc: lib/AP68040 at c5d5cc3 = apol/ap040x3 rtl overlay + ce_core re-gated to clkena_in; POST_STORES=1; FILL_CHANNEL=1 with both fill_ena low) -> black screen, no boot. The known-good bitstream build/stage_ap040_ddr3only (core 0e76761) boots to Workbench with the MMU on. Same board, same SD card, same firmware, reprogrammed back and forth over JTAG, so the board is fine and the x3 core is the culprit. Paul is asleep; nobody can look at the screen or press a key. You have the JTAG link and the ILA.

## Evidence so far (files in this directory)
- x3_now.txt / x3_now.csv: 4096 clk_114 samples, ~5 min after boot: dbg_pc = $00F815D2 constant, dbg_ir = 4E72 (STOP), dbg_flags = 0, as never low. That address is Exec's dispatcher idle loop (plan Log: "$F815BA-$F815D2, STOP #$2000"). Not halted, not faulted, not spinning: idle.
- x3_busy.txt / x3_busy.csv: triggered on the first bus request: the CPU wakes on the level-3 autovector ($6C -> $F81354), reads INTENAR = $602C, INTREQR = $0060 (VERTB | BLIT), ExecBase = $40000864 (fast RAM, board window at $40000000), walks the VERTB/BLIT server chain (btst #6/#5/#4, jsr (a5)). So interrupts are delivered and Exec runs; the OS is parked with no display.
- A "fault"-mode capture fired instantly with zero samples: a transient at programming time, not a fault.
- Kickstart is 46.143 (~/work/amiga/helloworld/kickstart/kick.a1200.46.143.rom); tools/kick_dis.py <rom> <start> <end> disassembles at Amiga addresses; match by opcode fingerprint before trusting it.

## What the benches did not model (read memory: sim-ddr3-cpu-bench-traps, in the report task-1-report.md section 6c too)
- sim/ddr3_cpu pulses FIVE enable phases (tb ~line 181); the RTL on hardware pulses FOUR (rtl/sdram/sdram_ctrl.v, commit 2f962f1). Every green x3 leg ran at a cadence the hardware does not use. Constraint: do NOT change the RTL cadence; if you change the bench, make it four-phase to match hardware (that is the honest configuration), and say so.
- The bench's 68k program is not Kickstart: no expansion.library ConfigDev walk, no CIA timer traffic, no copper/blitter, no interrupt taken while in STOP, no real graphics init. The D1 failure (plan, "D1 is written but does not boot") hung in expansion.library's ConfigDev walk on a bus-protocol corner the bench passed three times; the untested hypothesis there was the `slower`/chip-select spacing contract. Different change, same class of blindness.
- The x3 changes: ap040_cache.v (store-hit update in place X3.2, posted stores X3.3 with post_busy/post_err, C_IDLE bypass fix, fill channel X3.4 unreachable here), ap040_core.v (posted-store drain on MOVEC/PTEST/PFLUSH, interrupt sampler moved ~8 lines), ap040_mmu.v (walk_hold), compat top (fill_ok, ce_core). See `git -C lib/AP68040 diff 0e76761 c5d5cc3` and the x3 plan sections X3.2-X3.4 in ~/work/fpga/Xilinx/artix7/minimig/Minimig-AGA_MiSTer (`git show apol/ap040x3:AP040_IMPLEMENTATION_PLAN.md`). Nobody has ever run the x3 cache RE-GATED (ce = duty-cycled clkena_in): upstream runs it free-running. The posted store and the C_IDLE bypass are the two features whose timing relative to the bus handshake changes under a gated ce.

## Method (systematic debugging; the plan's own rule is "capture before theorising")
Phase 1: find WHERE the boot parks. Ideas, cheapest first: (a) a "now" capture is idle; use a trigger on something the boot does once and late -- e.g. the first write to DMACON $DFF096 with DMAEN, or to COP1LCH $DFF080, or BPLCON0 $DFF100 -- if it never fires within a minute, graphics never came up; (b) trigger on a write to $DFF09A (INTENA) sequence, CIA-B timer registers $BFDxxx (timer.device), or on a ROM address in expansion.library / graphics init found by disassembly; (c) compare with the SAME trigger on the known-good bitstream build/stage_ap040_ddr3only -- it has both ILAs too (built with ila=1), so every capture you design can be run on both cores and diffed. That A/B on the good core is your working example (Phase 2).
Phase 3: one hypothesis, one variable. The x3 features are switchable: POST_STORES is a parameter; check ap040_cache.v for parameters guarding the store-hit update and the C_IDLE bypass (upstream A/B'd each with a switch). An A/B build with one feature off is a legitimate minimal test (30 min); at most FOUR builds tonight. Prefer a bench reproduction over a build when you can construct one from the capture (the bench can run Kickstart-like sequences if you write them in sim/ddr3_cpu/asm; a 68k program that reproduces the parked state is the deliverable that makes the fix reviewable).
Phase 4: the fix. If the root cause is in the x3 cache under a gated ce, the fix goes into lib/AP68040 as a third commit on x3-overlay (documented divergence), or as a parameter setting in TG68K.vhd if a switch suffices; the bench that catches it is part of the fix. If the root cause is in the wrapper (TG68K.vhd) or the bench cadence, fix there. Then: core suite, the three positive sim legs + two mutants + control, build ila=0, program, and verify boot by ILA (a capture that distinguishes booted-to-Workbench from parked -- you will have built exactly that in Phase 1).
